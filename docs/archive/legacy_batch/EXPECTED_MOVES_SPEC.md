Expected Moves (EM) Page Architectural SpecificationProject Goal: To create an End-of-Day (EOD) analytical tool that calculates the options-implied expected price range for key market indices and ETFs for the Next Trading Session and Weekly Expiration, and provides a Confidence Score derived from the Cboe 1-Day Volatility Index (VIX1D). The system runs once daily after market close to ensure data integrity.Target Instruments: SPY, QQQ, IWM, DIA, SPX, NQ.Target Expirations: ODTE (Next Business Day) and Weekly (First standard weekly expiration after today).Phase 0: Discovery, Tooling, and Data SourcingThe objective of this phase is to establish secure data connections and define the exact data structures.0.1 Data Sourcing & API MappingData PointSourceAccess MethodNotesOption Chain Data (IV, ATM Prices, T)massive.com (REST API)Scheduled EOD FetchMust retrieve the entire chain or targeted strikes (ATM) for 6 tickers * 2 expiries = 12 total chains/requests. This delay is critical to ensure all EOD auction data and final prices are ingested and stable in the data source.Expiration Date Determination: MUST use the Trading Day Calendar (0.1) to find the correct:ODTE Expiration: The next valid trading day's expiration date.Weekly Expiration: The first standard weekly options expiry date (usually Friday) that falls on or after the ODTE date.Ticker Loop: Implement an asynchronous loop that iterates through all 6 target tickers (SPY, QQQ, IWM, DIA, SPX, NQ).API Requests (Batching): For each ticker, use the two calculated expiration dates from step 2 to retrieve the EOD Options Chain and EOD Underlying Close Price from the massive.com API.VIX1D Fetch: Fetch the EOD closing price for VIX1D using yfinance or the designated data source.Error Handling: Implement exponential backoff for API retries and robust error logging for 4xx/5xx responses from massive.com.1.2 Expected Move Calculation Logic (Core Functions)The logic must operate immediately after successful data ingestion for a given ticker/expiry pair.A. Straddle-Based Expected Move (Primary EM)$$EM_{\text{Dollars}} = (\text{ATM Call Midpoint Price}) + (\text{ATM Put Midpoint Price})$$ATM Identification: Identify the At-The-Money (ATM) strike as the strike price closest to the Underlying Closing Price (underlying_price from EOD fetch).Price Midpoint: Use the midpoint of the EOD Bid/Ask spread for both the call and the put to calculate the straddle price, ensuring a conservative estimate.B. IV-Based Expected Move (Verification)$$EM_{\text{Dollars, IV}} = \text{Underlying Price} \times \text{ATM IV} \times \sqrt{(\text{Days to Expiration} / 365)}$$Validation: If $|EM_{\text{Straddle}} - EM_{\text{IV}}| > 5\%$, raise an internal alert, but use $EM_{\text{Straddle}}$ for display, as it directly reflects the market cost/break-even.C. Confidence Score Calculation (VIX1D)We will establish a simple, normalized inverse relationship using a defined Min/Max range for VIX1D.VIX1D Range: Define a representative operating range (e.g., $\text{VIX1D}_{\text{Min}}=5$, $\text{VIX1D}_{\text{Max}}=30$).Normalization:$$\text{Confidence} = \text{MAX}\left( 0, \text{MIN}\left( 100, 100 \times \left( \frac{\text{VIX}_{\text{Max}} - \text{VIX1D}}{\text{VIX}_{\text{Max}} - \text{VIX}_{\text{Min}}} \right) \right) \right)$$Interpretation: A VIX1D of 5 yields 100% confidence. A VIX1D of 30 yields 0% confidence. VIX1D above 30 also yields 0%.1.3 Data Persistence and Caching (Firestore)The calculated data will be stored immediately upon EOD calculation for fast retrieval by the frontend.Data Structure: A single collection for the calculated results: /expectedMoves/data/{ticker}_{expiry_type}.Write Operation: After successful calculation (1.2), the system writes the complete output schema (0.2) to its corresponding Firestore document.Security Rule: Ensure the rules allow public reads but restrict writes only to the authenticated backend service ID.Phase 2: Frontend Interface (Presentation Layer)The frontend will be built to be fully responsive and focus on visual clarity and immediate actionability.2.1 Component ArchitectureMain Dashboard (ExpectedMovesPage): A responsive grid layout organized by ticker, containing two cards per ticker (ODTE and Weekly).Ticker Card (EMCard): Displays the calculated data for a single Ticker/Expiry pair.Reliability Dashboard (EMReliabilityPage): A new view (Phase 4) for historical data and statistical summary.2.2 Visual Design ElementsThe page must present 12 data sets clearly. This captures the pre-trade data point.4.2 Post-Expiration Processing ServiceScheduled Job: Implement a daily/end-of-week scheduled backend task (e.g., a simple cron job or cloud function).Lookup: The job queries the /history/ collection for all documents whose options expiration date (expiry_date derived from the chain) is today or has passed (e.g., within the last 48 hours).Realized Data Fetch: For each expired EM record, use the massive.com Stock/Index API to fetch the Open, High, Low, and Close (OHLC) for the underlying ticker on the expiration day.Update Document: Update the corresponding historical Firestore document with the fetched OHLC data.4.3 Reliability Metrics Calculation (Finalization)Immediately after fetching OHLC data (4.2), the system calculates and updates the following metrics in the historical document:Closed Within EM: A boolean flag.closed_within_em = realized_ohlc.close is $\ge$ lower_range AND $\le$ upper_range.Breach Metrics (High):high_breach_amount: $\text{MAX}(0, \text{realized\_ohlc.high} - \text{upper\_range})$high_breach\_percent: $\frac{\text{high\_breach\_amount}}{\text{expected\_move\_dollars}} \times 100$Breach Metrics (Low):low_breach_amount: $\text{MAX}(0, \text{lower\_range} - \text{realized\_ohlc.low})$low\_breach\_percent: $\frac{\text{low\_breach\_amount}}{\text{expected\_move\_dollars}} \times 100$4.4 Frontend Reliability DashboardStatistical Summary: Display key aggregate metrics for each ticker/expiry type:Hit Rate %: Percentage of times the EM successfully contained the closing price (closed_within_em = true).Average High Breach: Average dollar amount of upward breaches.Max Breach (%): The largest percentage overshoot/undershoot recorded.Historical Table: A searchable and filterable table displaying individual EM trades with their Calculation Timestamp, Expected Range, Realized Close, and Closed Within EM status.
